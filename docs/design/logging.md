# 分析日志：给数据科学家用的日志模块

> 总览见 [architecture.md](../architecture.md)，决议见 [roadmap.md](../roadmap.md)（#53–#55），路线节点 LOG1、LOG2。运行形态见 [runtime.md](./runtime.md)。

## 1. 定位

系统里有三种「日志」，用途不同，不能混成一份：

| 种类 | 给谁看 | 内容 | 保留 | 在哪 |
| --- | --- | --- | --- | --- |
| 运行日志 | 用户、排障的工程师 | 一次 Assignment 的实时输出 | 短：每个 Assignment 一个 Ring Buffer（10,000 条 / 5 MB） | [executor.md](../contracts/executor.md) 的 `log` 事件 |
| 审计 | 租户管理员、合规 | 谁在何时对什么做了什么、是否经人批准 | 长，不可改 | [gateway.md §2](./gateway.md#2-一次调用的流程)、[admin.md](./admin.md) |
| **分析日志**（本文） | **数据科学家** | 每个工单从触发到结束的完整轨迹，加上事后的结果 | 中到长，按敏感级别不同 | 本文 |

分析日志要回答的问题：

- **质量**：哪类任务做得成、哪类做不成？MR 被合并的比例、被人打断的比例、返工几轮？
- **准入**：Eval 的判断准不准？observe 模式下记录的候选里，有多少本该接、多少是噪音？
- **成本与速度**：每个工单花了多少 Token、多少时间，花在哪一步？
- **对比**：换一个 Prompt 版本、模型或执行内核，结果变好还是变差？
- **数据集**：从真实轨迹里挑出评测集和回归用例。

它不负责：实时告警（归监控）、合规取证（归审计）、给用户看的日志视图（归运行日志）。

## 2. 最重要的约束：内容分级

系统对租户的承诺是「平台运营人员默认看不到租户内容」（[admin.md §3.1](./admin.md#31-运营人员与租户内容的隔离)），以及「本地文件默认不上行」（[runtime.md §4](./runtime.md#4-本地数据默认不上行用户主动上传)）。数据科学家想要的恰恰是内容。所以每个字段在定义时就必须标明敏感级别（roadmap #53）：

| 级别 | 含什么 | 例子 | 谁能用 |
| --- | --- | --- | --- |
| **L0 度量** | 只有数字、枚举和内部 ID | 耗时、Token 数、状态、阶段、模型名、工具名、返回码、是否合并 | 我方数据科学家可以跨租户使用 |
| **L1 结构** | 行为的形状，不含原文 | 调了哪些工具、顺序、参数的**大小与类型**、文件扩展名、改动行数、错误类别；文本只留长度和哈希 | 同上，但只能以去标识后的租户编号出现 |
| **L2 内容** | 原文 | 提示词、模型输出、代码、命令与输出、评论正文、文件路径 | **默认只属于租户**，留在该租户的数据空间里，用租户密钥加密；我方使用须经租户授权（§6） |

规则：

- **没有标级别的字段不允许入库**，采集端直接拒绝（Fail-Closed）。
- 级别只能在采集端定，下游不能把 L2 降成 L1；需要 L1 就在采集时另外算一份（长度、哈希、类别）。
- **本地执行**（`local_dir`）只上行 L0 与 L1，L2 留在用户电脑上，与 #36 一致。用户主动上传的内容才产生 L2。
- 凭据在任何级别都不应出现；采集端按凭据特征扫描，命中即整段替换并计数。

## 3. 数据模型：一个工单一条轨迹

采用**轨迹（Trace）加事件（Event）**的模型，层级与现有概念一一对应，不发明新的 ID：

```text
Thread ─ Ticket（一条轨迹）
          ├─ 准入：Trigger → Eval 裁决（Fast Path / Slow Path、依据、模式）
          ├─ Assignment 1（一个跨度）
          │    ├─ 模型调用 × N（模型、Token、耗时、结束原因）
          │    ├─ 工具调用 × N（工具名、耗时、结果类别）
          │    └─ 工具网关判定（放行 / 审批 / 拒绝）
          ├─ 人类输入：打断、补充、审批结果
          ├─ Assignment 2（resume）…
          └─ 结果：MR / PR 的最终状态、人的处置、之后的返工
```

**统一信封**（所有事件共有的字段，全部是 L0）：

| 字段 | 说明 |
| --- | --- |
| `eventId` | 全局唯一，用于去重 |
| `schema`、`schemaVersion` | 事件类型与版本 |
| `occurredAt`、`seq` | 发生时间；同一 Assignment 内的序号，用来发现丢失 |
| `tenantId`、`botId`、`ticketId`、`assignmentId` | 归属，沿用现有 ID |
| `traceId`、`spanId`、`parentSpanId` | 轨迹关系；`traceId` 就是 `ticketId` |
| `source` | 谁发的：Bot 服务、工具网关、模型网关、Executor、应用 |
| `workspaceKind` | `cloud_project` 或 `local_dir` |
| `variant` | 当时生效的版本：Prompt 版本、策略版本、模型、执行内核及其版本、功能开关（§5） |

**事件清单**（首版）：

| 事件 | 来源 | L0 / L1 字段 | L2 字段 |
| --- | --- | --- | --- |
| `trigger.received` | Bot 服务 | 渠道、事件类型、是否来自 Bot 账号、正文长度 | 正文 |
| `eval.decided` | Bot 服务 | 路径、裁决、准入强度、模式、耗时、Token | 裁决备注、送给模型的上下文 |
| `ticket.stage_changed` | Bot 服务 | 前后阶段、停留时长 | — |
| `assignment.state_changed` | Executor | 前后状态、原因类别、排队与准备耗时 | — |
| `model.called` | 模型网关；BYOK 与本地模型不经过网关，由内核适配层上报（只有 L0） | 模型、输入 / 输出 / 缓存 Token、耗时、结束原因、是否重试 | 请求与响应全文 |
| `tool.called` | Executor（内核适配层） | 工具名、耗时、结果类别、参数与输出的大小 | 参数与输出 |
| `gateway.decided` | 工具网关 | 外部系统、动作类别、判定、是否在 Mandate 内、审批等待时长与结果 | 动作内容 |
| `human.input` | Bot 服务 | 类型（打断 / 补充 / 停止 / 审批）、发生在哪个状态、文本长度 | 文本 |
| `report.produced` | Executor | 报告类型、改动文件数与行数、是否有 MR / PR | 报告正文、diff |
| `outcome.recorded` | Bot 服务 | 见 §4 | — |

`model.called` 与 `tool.called` 的字段命名对齐 OpenTelemetry 的 GenAI 语义约定（`gen_ai.*`），便于接入现成的工具。该约定仍在演进，且已迁到独立仓库（[open-telemetry/semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai)），实现时锁定一个版本。

## 4. 结果回填：数据科学最需要的那一列

一条轨迹做得好不好，往往在任务结束之后才知道。Bot 服务在工单结束后继续观察，并追加 `outcome.recorded` 事件（可以多次，取最新）：

| 结果 | 怎么得到 |
| --- | --- |
| MR / PR 的最终状态：合并、关闭未合并、仍打开 | 代码平台的 Webhook |
| 合并前人又改了多少（Bot 的提交与最终合并内容的差异行数） | 代码平台 API |
| 评审轮数、评审评论数 | 代码平台 Webhook |
| 人的处置：接受、补充输入、丢弃 | 应用里的操作 |
| 被打断次数、`resume` 次数 | 轨迹内统计 |
| 合并后一段时间内是否被回滚或紧跟修复提交 | 代码平台 API，延迟回填 |
| 用户的显式评价（点赞、点踩、原因） | 应用 |

这些全部是 L0，跨租户可用。有了它，L0 加 L1 就足以回答 §1 里大部分问题，不必碰内容。

## 5. 实验与对比

- 每个事件的 `variant` 记录当时生效的全部版本。分析时按它分组，不需要事后去猜。
- **分流单位是工单**，同一个工单从头到尾使用同一套版本（与「内核按 Ticket 固定」一致）。
- 分流由 Bot 服务在创建工单时决定并写进轨迹；租户可以关闭参与实验。
- 评测集来自真实轨迹：从 L2 中挑选并去标识后，登记为带版本号的数据集（§7）。

## 6. 谁能看什么

| 角色 | L0 / L1 | L2 |
| --- | --- | --- |
| 我方数据科学家 | 跨租户，租户以去标识编号出现 | 默认**看不到**。仅当租户开启「数据使用授权」后，可在受控分析环境中使用该租户的 L2 |
| 租户的数据科学家或管理员 | 本租户 | 本租户，可导出 |
| 成员 | 自己的个人 Bot | 自己的个人 Bot |
| 平台运营人员 | 聚合指标 | 看不到 |

**数据使用授权**（roadmap #54）：

- 租户级开关，默认关闭，由租户管理员在管理后台设置（[admin.md §4](./admin.md#4-租户管理后台)）；可以只授权团队 Bot，不含个人 Bot。
- 个人 Bot 的 L2 还需要所有者本人同意，租户管理员不能替成员授权（与 [runtime.md §7](./runtime.md#7-记忆) 的可见范围一致）。
- 授权后的 L2 先去标识（人名、邮箱、仓库地址、内网域名替换为占位符）再进入受控分析环境；该环境不能向外导出原文，每次查询留审计。
- 撤回授权后，已复制到分析环境的该租户内容在约定期限内删除。
- **私有化部署**：数据不出客户网络，我方数据科学家默认什么都看不到；客户可以选择导出 L0 / L1 给我方。

## 7. 管道

```text
事件来源                 采集               处理                    存储                     使用
Bot 服务      ┐                        ┌ 校验 schema         ┌ 租户轨迹库（L0–L2，       ┌ SQL 与笔记本
工具网关      ├─► 本地发件箱 ─► 事件总线 ─┤ 凭据清洗           ─┤   租户密钥加密）         ─┤ 数据集（带版本）
模型网关      │   （至少一次）            │ 按级别分流          │ 分析仓库（L0、L1，       │ 实验对比
Executor     │                        └ 结果回填关联         │   跨租户，列式）          │ 看板
应用         ┘                                              └ 受控分析环境（授权的 L2） └ 导出给租户
```

- **采集**：各来源用同一个 SDK 写事件，先落本地发件箱再发往事件总线，至少投递一次；下游按 `eventId` 去重。发件箱积压不阻塞主流程：**宁可丢日志，不可拖慢任务**，丢弃时记数并上报。
- **沙箱里的事件**：由 Executor 的内核适配层在沙箱外侧采集，不让 Agent 自己写分析日志，避免被 Agent 篡改或伪造。
- **处理**：校验 schema，未知字段或未标级别的字段拒收；凭据清洗；按级别分流到不同的存储。
- **存储**：
  - 租户轨迹库：对象存储，按租户与日期分区，用该租户的密钥加密。删除租户或成员时销毁密钥即可使内容不可读。
  - 分析仓库：只有 L0 与 L1，列式存储，面向跨租户的聚合查询。
  - 受控分析环境：经授权并去标识的 L2。
- **数据集**：从轨迹中筛选出的固定集合，有名字、版本、来源说明、筛选条件与敏感级别；评测与回归引用数据集的版本，而不是引用实时数据。
- **质量监控**：每日检查 `seq` 是否连续、轨迹是否有头有尾（有 `trigger.received` 却没有任何后续的比例）、各来源的事件延迟、schema 拒收率。

## 9. 与其他部分的关系

- [executor.md §6](../contracts/executor.md#6-事件保留与截断)：契约新增 `activity` 事件，每次工具调用或模型调用一条，只含度量与结构，本地执行也上行；`tool.called` 与不经网关的 `model.called` 由它得到。`log` 仍然只用于界面，不进分析日志。云端执行的 L2 由 Executor 直接写入租户轨迹库，不经 `StreamEvents`。
- [gateway.md](./gateway.md)：审计记录与 `gateway.decided` 来自同一次判定，但写两份、存两处：审计不可改、按合规保留；分析日志可按保留期删除。
- [background.md §6.5](./background.md#65-内核适配层)：每个执行内核的适配层必须产出同一套 `model.called`、`tool.called` 事件，否则不同内核无法比较。这是内核适配层的一项必备能力。
- [admin.md](./admin.md)：用量统计由 L0 聚合得到，不另建一套计量（该文档 §9 第 1 题）。
- [gitlab.md §4](./gitlab.md#4-事件到工单的映射)：MR 合并、关闭、评审评论既推进工单，也是结果回填的来源。
- [web-app.md §4](./web-app.md#4-工作台w1)：用户评价的入口在会话视图里。
- [deployment.md §2](./deployment.md#2-设计约束不依赖-saas-专有设施)：事件总线与分析存储在私有化下的替代方式。

## 10. 待定问题

1. **数据科学家是谁**：本文按「主要是我方，同时支持租户自己的」来写。如果首版只服务我方，§6 的租户导出可以后做。
2. **L1 是否足够安全**：工具名、文件扩展名、改动行数的组合，在小租户里可能推断出项目信息。是否对低于一定规模的分组不展示？
3. **去标识做到什么程度**：代码里的业务名词、内网地址很难清干净。受控环境加禁止导出是主要手段，去标识只是辅助。
4. **事件总线与仓库的技术选型**，以及私有化部署时的最小形态（单机下可以退化为一张表加定时导出）。
5. **保留期**（§8）需要法务与客户合同确认。
6. **评价入口**：用户的点赞点踩放在应用的哪里，是否也接 IM 里的表情回应？

## 11. 实施要点

| 节点 | 任务 | 验收 | 风险与回退 |
| --- | --- | --- | --- |
| LOG1 | 事件规范（信封、事件清单、每个字段的敏感级别）、采集 SDK、发件箱、凭据清洗；Bot 服务与 Executor 先接入；L0 入库 | 一个工单从触发到结束能按 `ticketId` 查出完整轨迹；未标级别的字段被拒收；故意在输出里放一个假密钥，库里查不到；停掉事件总线不影响任务执行 | 与 BOT1、BG3 并行，越早接入越好：事后补不出历史数据 |
