# 部署设计：多租户 SaaS 与私有化

> 总览见 [architecture.md](../architecture.md)，决议见 [roadmap.md](../roadmap.md)（#19、#20），路线节点 D1。

## 1. 两种部署形态

> roadmap #45–#48：系统分**控制面**（Bot 服务、工具网关、管理面、模型网关）与**执行面**（每任务沙箱加家目录卷），见 [runtime.md](./runtime.md)。SaaS 与私有化部署的是同一套组件。

同一套代码，两种交付方式：

| 形态 | 适用客户 | 租户 | 运维方 |
| --- | --- | --- | --- |
| **多租户 SaaS** | 代码平台可从公网访问（GitHub、gitlab.com、对公网开放的自建 GitLab） | 多个租户共享一套部署 | 我方 |
| **私有化** | 自建 GitLab 等代码平台位于客户内网 | 单租户（一套部署只服务一个客户） | 待定（§5） |

判定规则：**代码平台在客户内网、不对外开放，就私有化部署**；不提供「SaaS 穿透进客户内网」的连接器方案。

两种形态使用同一套组件。SaaS 是多租户控制面加共享执行集群（或某个租户的专属执行集群，见 [runtime.md §2](./runtime.md#2-隔离) 的隔离档位）；私有化是同一套组件装进客户内网，只有一个租户，小规模时可以打包成**单机一体**形态。Bot 只在服务器端运行，桌面端不运行 Bot（见 [bot.md §5.4](./bot.md#54-部署单元多租户-bot-服务)）。

## 2. 设计约束：不依赖 SaaS 专有设施

为了能完整部署进客户内网，所有外部依赖都必须可替换：

| 依赖 | SaaS | 私有化 | 抽象方式 |
| --- | --- | --- | --- |
| Bot 服务数据库 | 托管 Postgres，每个租户独立的数据空间与加密密钥 | 客户自备或随包部署的 Postgres | 标准 Postgres 协议 |
| 共享层数据库 | 托管 Postgres（租户、模型目录、审计汇总） | 客户自备或随包部署的 Postgres | 标准 Postgres 协议 |
| 密钥管理 | 云 KMS / 密钥服务 | Vault、Kubernetes Secret 等 | 统一的密钥接口，`secretRefs` 只认引用名 |
| 沙箱运行时 | 我方执行集群 | 客户的 Kubernetes 或单机宿主 | Executor 只依赖一层沙箱接口，具体技术可替换（[runtime.md §8](./runtime.md#8-待定问题) 第 1 题） |
| 家目录卷 | 我方存储 | 客户的存储（持久卷或本机磁盘） | 标准卷接口 |
| 镜像仓库 | 公共 / 我方仓库 | 客户内网镜像仓库（可离线导入） | 镜像地址可配置 |
| SSO | 每租户配置 IdP | 客户内网 IdP | OIDC / SAML |
| 模型服务 | 租户模型目录（我方或租户提供的模型网关） | 租户模型目录指向客户允许访问的模型网关或内网私有模型 | 租户模型目录；桌面本地执行另用 BYOK |
| 事件总线 | 托管消息队列 | 随包部署的消息队列；单机形态退化为数据库里的一张表 | 采集 SDK 只依赖「追加写、按序读」的接口（[logging.md §7](./logging.md#7-管道)） |
| 分析存储（租户轨迹库、分析仓库） | 对象存储 + 列式仓库 | 客户的对象存储或本机磁盘；分析仓库可用同一个 Postgres 起步 | 标准对象存储接口与 SQL |
| 遥测与日志上报 | 开启 | 默认关闭，数据不出客户网络；客户可选择把不含原文的分析日志（L0 / L1）导出给我方，内容级（L2）不提供上报通道 | 开关配置 |

## 3. 各集成在私有化下的可行性

| 集成 | 私有化下 | 说明 |
| --- | --- | --- |
| 自建 GitLab | 可行 | 同在内网，Webhook 与 API 直连 |
| GitHub | 视网络而定 | 需要内网能访问 GitHub，并能接收 GitHub 的 Webhook（或改为轮询 API） |
| 飞书 | 可行 | 事件走长连接，只需要出站访问 |
| Microsoft Teams | **受限** | Bot Framework 需要从微软云**入站**访问一个公网 HTTPS 地址；客户需要开放一个入口，或经反向代理暴露回调地址 |
| 应用（Web / 桌面 / 移动） | 可行 | 部署在内网，员工经内网或 VPN 访问；桌面端的本地 Executor 反向连接到内网 Bot |

## 4. 交付物（节点 D1）

- 安装包：Helm Chart（Kubernetes）与 Docker Compose（单机试用）两种，包含控制面与执行面的全部组件
- 最小管理面（命令行 / 配置文件）与租户管理后台；**不含平台运营后台**（见 [admin.md §7](./admin.md#7-私有化部署)）
- 离线镜像包与导入脚本
- 配置模板：数据库、密钥后端、SSO、模型网关、各 Source 的凭据
- 版本升级与数据迁移流程（含回滚）
- 健康检查与巡检脚本（与 [bot.md §7](./bot.md#7-运维进程守护与故障自愈bot2) 一致）

## 5. 待定问题

1. ~~模型访问~~：已决议（roadmap #21）。云端执行用租户模型目录，私有化时目录指向客户允许的模型网关或内网私有模型；桌面本地执行用租户模型或 BYOK。执行内核 DSH 支持自定义端点（`openai-completions` / `openai-responses` / `anthropic-messages`），内网模型只要支持其中一种协议即可接入（见 [background.md §6.1](./background.md#61-模型路由)）。
2. **是否需要完全离线（air-gapped）**：完全离线时，镜像、依赖缓存（npm、pip 等）都要能在内网镜像源中获取。
3. **运维方**：私有化部署由客户 IT 运维、我方远程运维，还是两者结合？这决定了是否需要远程诊断通道。
4. **升级节奏**：私有化版本跟随 SaaS 同步发版，还是按季度等长周期发布？
5. **授权方式**：私有化如何计费与授权（License 文件、按席位、按并发）？
