# 运行形态：控制面、执行面与 Bot

> 总览见 [architecture.md](../architecture.md)，决议见 [roadmap.md](../roadmap.md)（#36–#39、#44–#52）。
>
> 本文是云端运行形态与 Bot 形态的**最新口径**，取代原来的「每租户一台虚拟机」（#35，已废止）与更早的「每租户一个 cell」（#24，已废止）。

## 1. 模型

把「Bot 住在哪」和「活在哪干」分开：

```text
控制面（多租户服务，常驻）
  Bot 服务    Router · Eval · Engine · Outbox · 记忆        Bot 是数据，不是进程
  工具网关    策略 · 审批 · 审计 · 连接器凭据
  管理面 · 租户模型网关 · 入口网关
        │ Executor 契约
        ▼
执行面（按需启动，用完即毁）
  每个任务一个沙箱：里面只有 Agent、执行内核和代码
  挂载持久的家目录卷：每个租户的团队一个，每个成员一个
  出口只通：租户模型网关、工具网关、白名单依赖源

用户电脑：本地 Executor（同一份契约，经入口网关连到 Bot 服务）
```

三条规则：

1. **Bot 是数据，不是进程**（#46）。Bot 的配置、规则、记忆、工单状态存在数据库里，由一组无状态的 Bot 服务实例按事件加载处理。创建一个 Bot 只是多几行数据，不占常驻进程。
2. **执行环境按任务创建，文件持久**（#47）。每个 Assignment 在一个新沙箱里运行，结束即销毁；沙箱挂载的家目录卷长期保留，装过的工具、克隆过的仓库、workdir 都还在。
3. **决策与凭据不进执行环境**（#45）。准入决定在 Bot 服务里做，连接器凭据在工具网关里；沙箱里的 Agent 读到恶意内容，也拿不到这两样东西。

团队 Bot 与个人 Bot：

| | 团队 Bot | 个人 Bot |
| --- | --- | --- |
| 家目录卷 | 团队卷（沙箱内挂载为 `/home/team`），团队 Bot 共用 | 成员卷（沙箱内挂载为 `/home/<成员>`），该成员的个人 Bot 共用 |
| 数量 | 多个 | 每个成员可以创建多个（默认上限见 §2） |
| 创建者 | 租户管理员 | 成员自己，无需审批 |
| 服务对象 | 整个团队 | 默认只有创建者本人 |
| 执行位置 | 只能云端 | 云端，或所有者已配对的电脑（§5） |

- **Bot 只在云端**，桌面端不运行 Bot（#33 仍然成立）。
- 个人 Bot 接入企业渠道、代码平台、租户模型时仍受租户管控（[admin.md §4](./admin.md#4-租户管理后台)）。
- 两种 Bot 对外部系统的写入、发送类操作都经过工具网关（[gateway.md](./gateway.md)）。

## 2. 隔离

| 边界 | 手段 |
| --- | --- |
| 租户之间（数据） | 每个租户独立的数据空间（库或 schema）与**独立的加密密钥**；Bot 服务的每次处理都绑定一个租户身份，跨租户访问一律视为不存在 |
| 租户之间（执行） | 沙箱不跨租户复用；家目录卷不跨租户挂载；沙箱之间网络互不可达 |
| 任务之间 | **每个任务一个沙箱**：进程互不可见，CPU / 内存 / 磁盘各有限额 |
| 团队与成员、成员与成员 | 各自的家目录卷；沙箱只挂载发起任务的那个 Bot 所属的卷 |
| 同一个卷下的多个 Bot | 默认共用一个卷（文件互相可见，进程不可见）。把 Bot 设为**「独立」**后，它使用自己的卷，其他 Bot 读不到它的文件（#47，原 #40 的新含义） |
| Agent 与凭据、决策 | 不在同一个环境：凭据在工具网关，决策在 Bot 服务 |

**沙箱的出口网络**默认只允许访问：租户模型网关、工具网关、租户管理员配置的依赖源（包管理镜像等）。`git` 的拉取与推送经工具网关代理。Agent 在 shell 里直接访问其他外部地址会被拒绝，因此绕不过工具网关。

**资源**：每个租户有并发任务配额；每个成员的个人 Bot 数量有默认上限（如 5 个，租户管理员可调）。空闲的 Bot 不消耗执行资源。

**租户隔离档位**（#48）：

| 档位 | 控制面 | 执行面 | 适用 |
| --- | --- | --- | --- |
| 默认 | 多租户共享，数据按租户隔离并各自加密 | 共享集群，每任务一个沙箱 | 大多数 SaaS 客户 |
| 专属 | 同上，或整套独立部署 | **独立的执行集群**，只跑这一个租户的任务 | 要求物理隔离的客户；「一家公司一台机器」在这一档提供 |
| 私有化 | 整套装进客户内网 | 客户内网；小规模可以是单机一体形态 | 代码平台在内网的客户（[deployment.md](./deployment.md)） |

## 3. 与 Executor 契约的关系

Bot ⇄ Executor 的契约（[executor.md](../contracts/executor.md)）的方法与状态机不变，变的是云端的实现：

| `workspace.kind` | 实现 | 位置 |
| --- | --- | --- |
| `cloud_project` | 云端 Executor：调度沙箱、挂载家目录卷、管理 workdir 与预览 | 执行面 |
| `local_dir` | 本地 Executor | 用户电脑上，主动经入口网关向 Bot 服务建立长连接 |

- 一个 Ticket 的多个 Assignment 落在**同一个 workdir**（在家目录卷里），但每个 Assignment 是一个新沙箱。`resume` 靠 workdir 与内核的会话记录续上，不靠沙箱常驻。
- 预览进程需要在 Assignment 结束后继续存活：用**带租约的保活沙箱**承载，到期或被 `StopPreviews` 回收（规则同契约的预览与 workdir 回收）。
- 契约里的 `tenantId` 是真正的隔离键，不再只是保留字段。
- 沙箱内不注入连接器凭据；模型访问用任务级的短期令牌经租户模型网关。

## 4. 本地数据：默认不上行，用户主动上传

> roadmap #36。

本地任务（`local_dir`）由云端的 Bot 调度，因此：

| 数据 | 是否离开用户电脑 |
| --- | --- |
| Assignment 状态、报告摘要、改动统计 | **自动上行**。Bot 在云端，没有这些无法推进工单 |
| 不含原文的分析事件：工具名、耗时、结果类别、大小、Token 数 | **自动上行**（分析日志的 L0 / L1，roadmap #53，见 [logging.md §2](./logging.md#2-最重要的约束内容分级)） |
| 日志、文件内容、diff 内容 | **默认不上行**，只留在用户电脑上；桌面端直接读本机。本地任务不产生内容级分析日志（L2） |
| 用户选中的文件、日志片段 | **只有用户主动上传时**才到云端，进入该成员的家目录卷 |
| 本地凭据、BYOK Key | 永不上行 |

- 没有自动同步，也没有任务迁移（roadmap #31）。口径与 cindy 一致：项目文件留在各自的电脑上，远程访问不是整盘同步。
- 使用租户模型时，提示词与代码上下文会发往租户模型网关用于推理；要求内容完全不出设备时只能用本地模型。

## 5. 手机经 Bot 控制远程电脑

> roadmap #37、#44、#51。

手机上的应用可以通过 Bot 控制一台**开机、装有桌面端且已配对**的远程电脑（如公司电脑）：

```text
手机应用 ──► Bot 服务（控制面）──► 远程电脑上的本地 Executor
           ◄── 状态 · 报告摘要 ──┘
```

- 手机上选择一台在线的设备和其中的本地目录，发起或跟进 `local_dir` 任务，可以补充输入、打断、停止，也可以处理审批卡片。
- 手机看到的是状态与报告摘要；日志和文件内容不经云端转发（§4），需要时由用户在电脑端主动上传。
- 设备必须在线；离线时工单停在 `person/delivery`。
- 不再需要手机与电脑之间的中转或直连协议（[web-app.md §6.5](./web-app.md#65-跨设备协议) 不再采用）。

**设备配对**（#44）：

- 本地 Executor 首次使用时，由已登录的成员在桌面端发起配对：桌面端显示二维码或配对码，成员在已登录的应用（Web 或手机）中确认。
- 配对后设备归属于该成员，出现在租户管理后台的设备列表中；成员与租户管理员都可以吊销。
- **本地执行只给个人 Bot**（#51）：只有设备所有者的个人 Bot 能派工给这台设备。团队 Bot 不能使用本地执行，因为团队 Bot 的会话与记忆对团队可见，本地任务的摘要不应进入团队可见的范围。
- 未配对或已吊销的设备无法建立长连接。

## 6. Bot 的两种形态

> roadmap #38、#50。借鉴 DS-Bot、OpenMausBot：Bot 是长期存在、像联系人一样对话的对象；同时保留原型的工单调度。

| | 团队 Bot：偏调度器 | 个人 Bot：偏联系人 |
| --- | --- | --- |
| 怎么被触发 | 盯代码平台与群聊里的事件（Issue、MR / PR、@、CI），按准入规则决定是否接手 | 成员直接和它对话 |
| 交互面 | 代码平台评论、IM 群聊、应用控制台 | 应用里的 Bot 列表与会话、成员绑定的 IM 私聊 |
| 典型工作 | 修 Issue、回应评审、跟进 CI | 调研、整理、写作、在自己的仓库里干活、定时任务 |

- **准入规则只有一套**（#50，[bot.md §3](./bot.md#3-准入三态模式与-mandate)）：白名单成员的明确请求是 explicit，其他来源默认 observe，Bot 账号只能产生 inferred 候选。两种 Bot 的区别只是白名单的默认值：**个人 Bot 的所有者默认在它的白名单里**，所以所有者的消息是 explicit；事件、别人的消息照样 observe。
- **工单是两种 Bot 共同的内部工作方式**：无论触发来自事件还是对话，需要执行时都创建 Ticket、经 Executor 契约派工（[bot.md §5](./bot.md#5-单写者-engine)）。
- 应用里所有 Bot 出现在同一个 **Bot 列表**中：成员能看到团队 Bot 和自己的个人 Bot，像联系人一样置顶、分组。
- 运行中可以随时发消息引导（即打断续跑）；不打断当前任务的旁问作为后续增强，不在首版范围。
- 多个 Bot 的群聊协同仍按 [bot.md §8.2](./bot.md#82-多-bot-协同参考未排期) 作为参考，未排期。

## 7. 记忆

> roadmap #39。借鉴 DS-Bot：记忆是 Markdown，用户可以直接查看和修改。

- 每个 Bot 有自己的记忆，内容是 Markdown，**存放在 Bot 服务的数据库里**（按租户加密，保留每次修改的历史），不放在家目录卷里，所以沙箱里的 Agent 改不了它。派工时由 Bot 服务把相关记忆放进 Prompt。
- 记忆记录的是**偏好、约定与长期事实**（如代码风格、常用分支、谁负责什么），不是对话全文。对话历史单独保存并可检索。
- 所有者可以在应用的 Bot 详情页查看、编辑、删除记忆，也可以直接告诉 Bot「记住」或「忘掉」。
- 团队 Bot 的记忆对团队可见，由租户管理员与被授权的成员维护；个人 Bot 的记忆只对所有者可见（管理员可见范围见下）。
- **记忆不参与准入判定**。它只是给 Agent 阅读的上下文，效力低于宿主强制的规则与策略（[bot.md §6](./bot.md#6-prompt-组装) 的优先级）；记忆中的文字不能改变权限。
- 记忆不随模板分发，也不随 Bot 导出（[bot.md §8.1](./bot.md#81-bot-模板专家)）。
- 记忆不存放凭据；写入时命中凭据特征的内容被拒绝。

**管理员能看到个人 Bot 的什么**（#52）：

- 默认只有元数据：有哪些 Bot、用量、经工具网关的对外动作审计。记忆与会话内容看不到。
- 租户可以开启「合规访问」开关，开启后管理员可按流程查看，成员界面会明示这一点，每次查看留审计。
- 成员离职：账号停用后，其个人 Bot 与成员卷冻结 30 天；移交给他人须走租户内流程；到期删除。

## 8. 待定问题

1. **沙箱技术选型**：微型虚拟机还是沙箱容器？需要评估隔离强度、冷启动时间（目标是几秒内）与私有化时的部署难度。首版可以先用沙箱容器，契约不变。
2. **家目录卷的并发挂载**：同一个卷可能同时被多个任务的沙箱挂载，需要支持并发读写的存储，或改为「每个任务只挂自己的 workdir 加一个共享只读缓存」。后者更安全，但装过的工具不能跨任务共享。
3. **依赖与环境的准备**：基础镜像加每个项目的 prepare command；依赖缓存放在卷里还是做成镜像层？[layerfs.md](./layerfs.md) 的分层方案在这个模型下重新成为候选。
4. **Bot 服务从原型移植的工作量**：取决于原型里 Router、Eval、Engine 的逻辑与 DSH 插件机制耦合多深，需要读原型代码后评估。
5. **「合规访问」的默认值**（#52）：默认关闭是当前口径；有的行业客户会要求默认开启。
6. **记忆由谁写入**：Bot 自动沉淀，还是只在所有者明确要求时写入？
7. **团队 Bot 是否默认「独立」**：默认共用团队卷更省事，默认独立更安全。
