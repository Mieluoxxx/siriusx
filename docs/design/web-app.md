# 应用设计：Web / 桌面端 / 移动端

> 总览见 [architecture.md](../architecture.md)，落地顺序见 [roadmap.md](../roadmap.md)（节点 W0–W2，以及 Bot 侧的 BOT6）。

## 1. 定位与边界

Web 和桌面端是**同一个应用**，功能一致，区别只在工作区放在哪里：

| 形态 | 工作区 | 执行方 | 节点 |
| --- | --- | --- | --- |
| **Web** | 完全云端：**云端项目空间** | 云端 Background（容器） | W1 |
| **桌面端** | 云端项目空间（与 Web 完全一致）或本地目录 | 本地 Executor（`local_dir`）/ 云端 Background（`cloud_project`） | W2 |
| 移动端 | 云端项目空间；或经桌面端访问本地目录 | 同上 | W2 评估 |

两种执行方实现同一份 [Executor 契约](../contracts/executor.md)，由 `workspace.kind` 路由，Bot 和应用界面不需要区分。

应用有两个面向：

| 面向 | 用户在做什么 |
| --- | --- |
| **工作台** | 管理项目空间、发起任务、和 Agent 对话、补充输入与打断、审查 diff、访问预览 |
| **控制台** | 回答「现在有没有事需要我处理」，查看系统健康与工作历史 |

在系统中的位置：

- 应用对 Bot 而言是**一个 Source**（和 GitHub、飞书并列）：应用里的会话就是一个 Thread，用户发的消息就是 Trigger，走同一套 Engine、准入和打断防抖。
- 同时应用也是 Bot 的**查询与操作 API 的消费者**，供控制台和配置使用。
- 应用不持有领域状态，数据与操作全部经过 Bot ⇄ 应用契约（W0）；客户端只导入契约类型，不耦合 Bot 实现。
- 工单阶段由 Bot 推导（[ticket-stage.md](../contracts/ticket-stage.md)），应用只负责展示。

### 1.1 模型来源

模型来源由**执行位置**决定，而不是由客户端形态决定：

| 执行位置 | 模型来源 | 凭据 |
| --- | --- | --- |
| 云端（Web；桌面端打开云端项目空间） | **租户模型目录**：租户管理员配置可用模型，按 SSO 用户 / 角色开放，用户在其中选择 | 租户统一管理，用户不可见，费用计入租户 |
| 本地（桌面端打开本地目录） | **租户模型目录**（经企业 SSO）、**BYOK**、或**本地模型**（如 Ollama） | 租户模型：本地 DSH 用 SSO 短期 Token 访问租户模型网关，上游 Key 不下发到设备；BYOK：Key 只保存在用户设备上；本地模型：无上游凭据 |

租户管理员可以**禁用 BYOK**，禁用后本地执行只能用租户模型或本地模型。

Bot 自身使用的模型（Router、Eval）始终来自租户模型目录，与用户的 BYOK 无关。

### 1.2 云端项目空间

Web 用户没有本地目录，项目空间是云端持久存在的工作区：

- 一个项目空间对应一个仓库（`projectId`），绑定执行环境（基础镜像与依赖缓存，见 [background.md §3](./background.md#3-执行环境)）。
- 在项目空间里发起的每个任务，按 Executor 契约获得独立的 workdir（与云端 Background 的 Ticket workdir 是同一个概念）。
- 项目空间的生命周期独立于任务：任务结束、workdir 回收后，项目空间仍然存在。

### 1.3 执行位置与数据边界

> 决议见 roadmap #31。原设想是「本地没做完的任务上传到云端继续做」，客户认为涉及隐私，该能力取消，由此确定下面的边界。

**执行位置只在任务开始时选择**，之后不能更改：

| 选择 | 工作区 | 代码从哪里来 | 可用形态 |
| --- | --- | --- | --- |
| **云端主机** | `cloud_project` | 云端主机从代码平台按 `baseRef` 检出 | Web、桌面端、移动端 |
| **本地客户端** | `local_dir` | 用户机器上的目录，含未提交改动 | 桌面端 |

规则：

- **选定后对该任务（Ticket）不可变**。同一个任务的所有 Assignment（含打断续跑、回答后续跑、workdir 被回收后的降级重建）都在同一个执行位置，使用同一个 `workspace`。
- **客户端的内容不上传到云端**。以下内容只存在于用户设备上，不会被同步、复制或打包到云端主机：
  - 本地目录中的文件与未提交、未推送的改动；
  - 本地凭据与 BYOK Key。
- **不提供任务迁移**：没有「把本地任务搬到云端继续跑」，也没有「本地目录上云」。
- **两个执行位置之间唯一的内容通道是代码平台**。想让云端接着做本地的工作：先把改动 push 到代码平台，再在云端项目空间新开一个任务；云端看不到未推送的内容。
- **设备离线不回退**：本地任务的设备离线时，工单停在 `person/delivery` 等待设备上线，不会改派到云端主机。

本地任务由云端的 Bot 调度，因此状态、报告摘要、改动统计会自动上行；**日志与文件内容默认只留在用户电脑上，只有用户主动上传的内容才到云端**（roadmap #36，见 [runtime.md §4](./runtime.md#4-本地数据默认不上行用户主动上传)）。

## 2. 应用作为 Source

| 项 | 规则 |
| --- | --- |
| Thread | 一个应用会话对应一个 Thread；会话里发起的任务对应一个 Ticket |
| 身份 | 应用 Source 用应用登录身份（SSO 用户 ID）维护自己的白名单；名单成员在应用中的请求为 **explicit**。不与 GitLab / 飞书 / Teams 身份映射（见 [bot.md §5.2](./bot.md#52-身份不跨-source-映射)） |
| 打断 | 任务运行中，用户在会话里追加的消息即人类输入，按 [executor.md §5.3](../contracts/executor.md#53-打断防抖按阶段区分) 防抖后打断续跑 |
| 指令 | 停止 / 续跑按钮与 GitHub 评论的 `/stop`、`/resume` 等价 |
| 回复 | Agent 的报告与提问回到发起它的应用会话 |
| 跨渠道 | 任务产生的 PR 照常在 GitHub 上；PR 上的评论经 GitHub Source 进入同一个 Ticket，应用会话里同步可见 |
| 来源标记 | `clientContext.channel = app`；`platform` 区分 web / desktop / mobile；`deviceId` 标识桌面设备 |

| 审查 | 查看 diff、跳转 MR / PR |
| 评价 | 每份报告下可以点赞 / 点踩并选原因；只记录评价本身，不附带会话内容（roadmap #55） |
| 文件浏览 | 在项目空间中**只读浏览**文件（Web 与桌面端相同；桌面端用户在应用外用自己的编辑器修改本地目录不受限制）：无任务时浏览代码平台上的项目；选中任务时浏览其工作现场（含未提交修改，标出改动过的文件）。不能编辑，不提供终端 |
| 预览 | 打开预览地址。预览默认只绑定宿主 `127.0.0.1`，Web 访问必须经过带鉴权的反向代理 |

## 5. 控制台（W1 核心 + 按需追加）

视觉层级按顺序回答三个问题：

1. 现在有没有事需要我人工介入？
2. 系统整体是否健康、是否在做正确的事？
3. 某项工作从 Trigger → Eval → Ticket 的完整历史是什么？

原则：

- **Quiet by default**：健康状态不占额外空间，一次性瞬态网络错误直接省略。
- **Honest state**：显示的计数必须精确等于其链接列表的实际长度。
- 破坏性操作一律二次确认。

### 5.1 标签页

W1 先做 Overview 与 Execution，其余按需追加。

| 标签页 | 内容 |
| --- | --- |
| **Overview** | 需人工介入的工单、系统故障、过去 24 小时活动计数、Executor 负载、缺失的初始化配置 |
| Source | 各监听源状态、24 小时内被过滤的 Trigger、被丢弃消息（标注原因并链接到工单或线程） |
| Trigger | 按 Subscribed / Evaluating / New Triggers in 24 h / All Threads 筛选线程；倒序 Triggers、退回原因、仅上下文订阅 |
| Eval | 每次裁决的原因与命中规则 |
| **Execution** | 全局 Pause processing；工单阶段筛选；Retry / Evaluate again |
| Settings | 按 Sources / Eval / Execution / Prompts / Deployment 管理配置与保存历史；升级改动了已被覆写的默认提示词时，并排对比，选择 Keep my text 或 Use the new default |

### 5.2 7 个阶段

推导规则见 [ticket-stage.md](../contracts/ticket-stage.md)。前四个 `person/*` 需要人类介入，在工作台会话列表和 Execution 页都置顶展示。

| Stage ID | 标签 | 人类动作 |
| --- | --- | --- |
| `person/delivery` | Input undelivered | 系统 2 秒后首次重试，指数退避至最高 1 分钟；可以点 Retry |
| `person/answer` | Awaiting answer | 在会话或原线程回答问题 |
| `person/review` | Awaiting review | 审查 diff / 预览后：云端项目「补充输入」（如提交 MR）或「丢弃」；有 MR / PR 时到代码平台审查；本地目录可「接受」 |
| `person/blocked_failed` | Blocked · Failed | 发消息或点 Retry，释放回执行 |
| `working/queued` | Queued | — |
| `idle` | Waiting for a Trigger | — |
| `working` | Working | 可以补充输入、打断或停止 |

## 6. 桌面端与移动端（W2）

桌面端是**同一个应用**加上本地能力；W2 的工作是实现这些增量，而不是另做一套界面。**桌面端不运行 Bot**：Bot 只在云端服务器（roadmap #33），本地只有 Executor，本地任务由云端 Bot 调度。

- **打开云端项目空间**：行为与 Web 完全一致，由云端 Background 执行，不依赖本地 Executor。因此桌面端打包可以早于本地 Executor 交付。
- **打开本地目录**：需要下面的本地 Executor。

### 6.1 桌面端相对 Web 的增量

| 能力 | 说明 |
| --- | --- |
| **本地 Executor** | 实现 Executor 契约（`workspace.kind = local_dir`），在用户机器上执行，可以使用本地凭据和未提交代码；上线时主动向 Bot 建立长连接并按 `deviceId` 注册。首次使用须由已登录成员扫码或输入配对码完成设备配对（roadmap #44）。见 [background.md §2](./background.md#2-计算--状态--机器三层解耦) |
| 本地文件修改追踪 | 按轮次追踪本地文件修改，支持撤销与重放 |
| macOS HUD 悬浮模式 | 分区透明度、鼠标穿透、快捷键恢复点击、截屏发送给模型 |
| Office 文档 | Agent 的本地工具能力：由 Agent 创建、检查、编辑 `.docx` / `.pptx` / `.xlsx`，应用只提供预览；不内置手工编辑器 |

本地 Executor 的安全边界：

- 回收 workdir 时**绝不删除用户指定的目录**，只清理自己创建的 worktree、临时目录和预览进程（见 [executor.md §7.1](../contracts/executor.md#71-workdir-回收显式调用--租约兜底)）。
- 设备离线时，Bot 收到 `EXECUTOR_OFFLINE`，工单进入 `person/delivery`，设备上线后自动重试。

### 6.2 移动端

使用云端项目空间与 Web 功能一致。手机还可以**通过 Bot 控制一台开机且装有桌面端的远程电脑**（如公司电脑）：选择在线设备与本地目录，发起、跟进、打断本地任务（roadmap #37，见 [runtime.md §5](./runtime.md#5-手机经-bot-控制远程电脑)）。手机上看到的是状态与报告摘要，日志和文件内容不经云端转发。是否自建原生移动端，还是用响应式 Web 覆盖，在 W2 评估。

### 6.3 Monorepo 结构

```text
apps/web                        Web 应用（工作台 + 控制台）
apps/desktop                    DSH Desktop 的薄 fork（roadmap #56），不自研壳
apps/mobile                     Expo / React Native（iOS / Android）
apps/cindy-headless/src/cli.ts  命令行无头入口
packages/*                      契约类型、auth、device-link、共享 UI 等
```

- **Smart Binary**：安装期按平台下载 Claude Code CLI、Codex CLI、ripgrep 等，SHA-256 校验后放到 `apps/` 专用目录。

### 6.4 执行内核与模型

执行内核可替换，首个实现为 **DSH**（roadmap #32，见 [background.md §6.5](./background.md#65-内核适配层)）：**本地内核固定为 dsh**（桌面端即 DSH Desktop 的薄 fork，roadmap #56），云端可以替换为其他内核（首批 dsh 与 pi，备选 codex 与 claude），都经同一套内核接口接入（roadmap #57），**内核按任务固定**。原蓝图中「在任务中途切换内核」仍不采用；任务中途可以切换模型（在允许的模型来源内）。

模型来源见 §1.1：云端执行用租户模型目录；本地执行用租户模型目录或 BYOK。

> 原蓝图中的「复用 Claude Code / Codex 订阅」「本地模型 + Skip Sign-In 纯本地模式」在 ToB 场景下是否保留，见 §7 第 7 题。

### 6.5 跨设备协议

> **不再采用**（roadmap #37）：手机经 Bot 控制远程电脑，不需要手机与电脑之间的中转或直连。本节保留作为原蓝图记录。

- 默认经云端 Relay 互联，同局域网自动升级 WebRTC P2P；文件留在宿主机，按需远程访问。
- 移动端到桌面端的 IPC 受默认拒绝白名单管控。
- 协议包必须兼容 React Native（禁止 `node:*`）、零运行时依赖。
- Relay 静默丢弃未知 `EnvelopeKind`（发送端表现为超时黑洞），因此协议演进优先**仅追加可选字段**并定义降级行为；确需新增转发帧时，双端同步升级 `EnvelopeKind` 与 `PROTOCOL_VERSION`。
- 每次协议变更必须同时提交：类型定义 + 带字段路径的运行时解析校验 + 覆盖 roundTrip 与坏帧拒绝的单元测试。

### 6.6 插件沙箱

客户端插件打包为 `.cindy` ZIP，根目录直接包含 `ghost.json`、`main.js` 和资源。四项原则：

1. 默认运行于隔离沙箱，凭宿主签发的在途 `callId` 执行常规 HTTPS 和工作目录操作；自主后台或长生命周期 Node 进程须在 `ghost.json` 中显式声明 `direct` 与 `node` 边界。
2. 普通 API Token 存入宿主只写 `/secrets` 通道；Node 插件所需明文凭据经 `node.secretBindings` 限定在特定 Worker 方法内瞬态注入，不得流经浏览器 `main.js`、Agent 参数或日志。
3. `ghost.json` 中的工具描述是 Agent 必须遵循的行为契约。
4. 面向用户的报错必须转成可执行的人话指引（如 401 要明确提示去哪里填 Token）。

## 7. 待定问题

已决议：

- Web 完全云端，部署在公网，鉴权、HTTPS、预览反向代理都是必需项。
- 产品为 **ToB**，以多租户 SaaS 为主，内网客户私有化部署（见 [deployment.md](./deployment.md)）；应用鉴权走 **SSO**（OIDC / SAML），每个租户配置自己的 IdP（如 Entra ID、飞书、Okta）。
- 必然是多用户；租户内的角色与权限（RBAC）见第 5 题。

1. ~~登录方式~~：已决议为按租户配置的 SSO。待定：首批支持哪些 IdP 协议（建议 OIDC 优先，SAML 次之）。
2. **项目空间是否等于 Git 仓库**：只支持从代码平台（GitHub / GitLab）的仓库创建，还是也允许非 Git 项目、上传文件？
3. ~~项目空间里能否直接操作~~：已决议（roadmap #27）：**只能浏览文件**，不能编辑，不提供终端；修改只能通过 Agent。
4. **应用发起的任务是否必须关联代码平台的 Issue**：不关联时，代码平台上的人在 MR / PR 出现之前看不到任务的来龙去脉。
5. **租户内的共享与权限**：项目空间和会话是私有的还是租户内共享的？其他成员能否在别人的会话里补充输入或打断？~~需要哪些角色~~：角色已在 [admin.md §2](./admin.md#2-角色) 定义（平台运营 / 租户管理员 / 成员）；共享范围仍待定。
6. **本地目录的隔离方式**（W2）：本地 Executor 是直接在用户目录里修改，还是在目录内建 worktree 隔离？前者符合桌面用户的习惯，后者支持多任务并行。
7. ~~桌面端的其他模型路由~~：已决议（roadmap #23）：允许本地模型，管理员可禁用 BYOK。~~是否允许不登录 SSO 的纯本地模式~~：已决议（roadmap #58）：允许。不登录即个人版，只有本机原生对话；登录即受组织管理，原生对话保留但标为「个人、不审计」，租户管理员可关闭。待定：管理员是否也需要能禁用本地模型。
8. ~~本地任务有哪些数据可以经过云端~~：**已决议**（roadmap #36、#37）。状态、报告摘要、改动统计自动上行；日志与文件内容默认只留在设备上，只有用户主动上传的才到云端；手机经 Bot 控制远程电脑，不做文件中转。决议前的分析保留如下：「客户端内容不上传」已确定不同步文件、不迁移任务。但按现有设计，本地 Executor 连接的是云端的租户 Bot，以下数据会离开设备，需要逐项决定：

   | 数据 | 现有设计 | 待定 |
   | --- | --- | --- |
   | Assignment 状态、报告摘要、`diffStats` | 存入租户 Bot | 控制台与跨渠道回复依赖它，建议允许 |
   | 日志（`log` 事件，含 Agent 输出与命令输出，可能带代码片段） | 经 `StreamEvents` 进入 Bot | 只留在设备上、应用直连设备读取，还是允许上行但不持久化？ |
   | 文件浏览与 diff（`ListFiles` / `ReadFile`） | 应用经 Bot 调用本地 Executor | 桌面端应直接读本机，不经云端；其他设备（移动端、Web）是否允许远程查看？ |
   | 模型请求（`model.source = tenant`） | 提示词与代码上下文发往租户模型网关 | 属于推理而非存储，但内容确实离开设备；要求完全不出设备时只能用 `local` 模型 |
   | 移动端经 Relay 访问桌面端文件（§6.2、§6.5） | 云端 Relay 转发 | 转发不落盘是否可接受，还是只允许局域网 P2P？ |

   Bot 只在云端服务器（roadmap #33），本地任务一定由云端 Bot 调度，所以第一行的状态与报告**必然**经过云端；可以选择的只有后四行。
